# GridNexa Coding Agent：对标 Genspark Code 的实现路线

版本：规划草案 v0.1。基准日期：2026-11-25。本文只规划，不代表以下能力已经实现，也不代表技术选型已获最终确认。

## 一、先确定我们在做什么

用户明确的目标是把 Eve 模板演进为工业级 Coding Agent 产品，并在逐步实现中学习产品与工程方法；对标对象是 Genspark Code，而不是仅针对本地目录工作的 GenCode。

建议的产品定位是：面向希望构建 Web 应用的个人开发者与小团队，在浏览器中描述需求，让 Agent 在隔离工作区内生成和修改真实代码，执行验证，提供可访问预览、版本恢复、代码导出和受控发布。首版优先证明这个完整闭环，不承诺立即覆盖 Genspark 的全部项目类型。

首版默认范围是单一 Web 技术栈、单项目串行写入、单模型、单沙箱供应商、单发布供应商。登录、资源授权、执行隔离、预算上限和源码持久化不是后期加分项，而是试用用户接入前的必要条件。Android、Shopify、自带 SSH、多语言任意仓库、实时多人编辑和多 Agent 并发修改暂不进入首版。

上述首版范围是为降低学习和调试复杂度而提出的建议，尚不是用户逐项确认的需求。若后续确定主要用户是专业开发团队而非应用创建者，应调整已有仓库与 PR 工作流的优先级。

### 对标事实与规划边界

Genspark 官方 Code 页面和帮助中心描述了从提示词创建网站、全栈应用、Android 应用、处理已有代码、实时预览、文件编辑、Save Points、源码导出和发布的工作流。其帮助中心也明确区分 Genspark Code 与 GenCode。[S1][S2]

不能据此推断其内部模型编排、数据库、调度器或沙箱供应商。官方页面称现有 GitHub 项目与新建 Web 项目的体验不同，前者没有 Preview 和 Publish 标签；不能把所有产品类型的功能简单合并成一张强制实现清单。官方还说明代码回退不等于数据库回退，开发数据与线上数据分离，且当前没有独立 staging 站点。[S1]

本项目借鉴的是用户闭环，不是复制每一个界面标签或默认安全策略。后文提出的默认私有预览、显式发布审批、staging、预算控制与版本绑定部署属于我们的设计建议，不是对竞品现状的断言。

## 二、仓库事实：起点和可复用能力

当前 authored Agent 逻辑主要是 `agent/agent.ts`、`agent/instructions.md` 和 `agent/channels/eve.ts`。身份说明仍是通用模板，没有 authored 业务工具、前端工作台、项目数据库、应用发布流水线或评测用例。`package.json` 有 `eval` 脚本不代表已有评测；安装 `@vercel/connect` 不代表已有外部连接。[L1][L2]

主 Agent 已选择 `alibaba/qwen3.7-flash`，推理配置为 `medium`。遵循 `AGENTS.md`，保留现有选择，先验证真实工具调用与编码效果，不因其他模型名气而直接替换。模型 ID 当前可用性、账号权限、视觉能力和真实成本均未在本轮运行验证。[L1]

根依赖声明 Eve `^1.5.0`，本地安装及 lockfile 对应 1.5.0；Node 要求为 26.x。后续实现以该版本本地文档与公开 API 为准，升级另做兼容性验证。[L2]

Eve 并非只有聊天接口：其文档已有默认文件与命令工具、持久执行、会话与事件流、沙箱、审批、React 接入和 evals。优先复用这些基础能力，不先自建第二套 Agent loop、消息流协议或持久化任务引擎。[L3]–[L8]

必须补齐的产品层是用户与项目归属、每个资源的访问控制、项目级源码和版本、项目与 session 的映射、预览管理、发布管理、使用量账本和运维流程。框架能力不等于本项目已经配置、验证或具备相应生产保障。

### 四条不能误判的框架边界

现有 `eve` channel 的 `vercelOidc()`、`localDev()`、`placeholderAuth()` 不构成生产浏览器用户登录。Eve 的 route authentication 也不提供 per-session ACL，必须检查调用者是否有权访问目标项目和 session；读取事件流、继续对话、取消任务也都需要授权。[L1][L7]

Eve 会话状态与运行事件不等于永久项目存储。默认保留和会话结束清理行为必须核实、配置；不能依赖一个 session 永远存在来保存用户代码和审计记录。[L3][L4]

沙箱停止后文件保留与进程恢复是两件事。文档所述默认空闲停止会结束进程，恢复时不能假设开发服务器自动启动；会话结束或供应商资源丢失还可能导致沙箱删除。项目源码必须有独立的持久真源。[L5]

自定义工具的 `execute` 在应用 runtime 中运行，不是自动在沙箱中执行。只有显式经沙箱 API 执行的用户代码才进入隔离环境。不能把工具代码里的直接文件系统访问或命令执行暴露给模型。[L6]

## 三、目标架构：先分清职责，再决定组件

### 控制面、执行面与发布面

浏览器工作台负责项目、对话、文件、diff、预览、版本和发布状态。平台 API/BFF 负责登录、资源授权、项目配置、Run 记录、预算和事件适配。Eve runtime 负责模型调用、工具循环、会话流、审批和持久执行。沙箱执行面运行生成代码、安装依赖、构建、测试及预览进程。发布面从不可变源码版本创建独立构建产物，将审核过的版本发布到托管环境。

调用路径为：浏览器 → 平台授权边界 → Eve session/工具 → 隔离沙箱；项目元数据、源码快照和发布记录进入持久存储。预览经授权网关访问，每个项目或隔离工作区使用不同 origin，不与平台登录页面共享 origin 或高权限 cookie，也不让不同项目仅按同一域名的路径区分。预览票据、cookie、缓存与 Service Worker 的作用域不得跨项目。

建议 Web 工作台使用 React/TypeScript，可评估 Next.js；被生成的应用先固定为 React + Vite + TypeScript 模板。平台元数据可选 PostgreSQL，源码快照与构建产物使用对象存储，版本关系记录在数据库。它们是默认候选，不是模板已有依赖，P0/P1 要基于部署限制与成本记录 ADR 后再选择。

用公开 `eve/react` 和 `eve/client` 评估工作台接入，沿用 Eve session 和可重连事件流；平台 Run 是业务记录，不是替代 Eve 工作流的第二个执行器。项目数据库存引用和产品状态，不重复保存一份可独立驱动 Agent 的完整执行栈。[L3][L8]

沙箱候选优先从 Eve 支持的 provider 及 registry 中筛选，以隔离、端口访问、恢复、网络策略、区域和成本为依据做一次小验证。不要仅因本机 `child_process` 容易实现，就把它当作面向用户的隔离执行方案。涉及外部服务集成时，先按 `AGENTS.md` 查 registry；agent 本身的 Vercel link/deploy 使用 Eve 命令。[L9]

### 最小领域模型

`User` 与 `ProjectMembership` 确定主体及角色；`Project` 持有模板版本和当前源码版本；`Run` 关联项目、发起者、Eve session、起始 revision、预算和终态；`Workspace` 描述项目当前沙箱及恢复状态；`Revision` 指向不可变源码快照及校验值；`Artifact` 记录构建、测试和截图等证据；`Deployment` 固定关联 revision、构建产物和环境；`UsageEntry` 记录可核对、可去重的用量。

平台项目的用户权限与被生成应用的业务用户权限是两套身份域。P5 生成的登录系统不能自动复用平台会话或让生成应用读取平台凭据。项目默认个人所有，先提供 owner 权限；只读共享或协作者角色在实现之前不得通过前端隐藏按钮来冒充授权。

一个项目允许多个历史 Run，但首版同一时间只允许一个写入者。UI 手动编辑、Agent 修改和版本恢复共享项目租约与 revision 前置条件。多个浏览器标签页也要遵守这一约束，不只禁止多个 Agent。租约必须携带单调递增的 fencing token，提交 revision、更新状态和发布时均校验；不能检查后再无保护地写入共享可变工作区。失联执行者可能仍在运行，恢复尝试需使用隔离的 attempt 工作区并按有效 token 提交，或先确认旧执行环境已停止；租约过期本身不是旧进程已死亡的证据。

### 状态、幂等与事实来源

建议平台 Run 状态为 `queued → running ↔ awaiting_approval → succeeded / failed / cancelled / interrupted`，所有非终态均可按合法规则结束；构建、验证和预览就绪是阶段事件，不是互相替代的业务终态。只保存面向用户的操作摘要、工具输入输出摘要与证据，不要求保存模型私有思维链。

每次启动 Run 都记录 `runId`、幂等请求键和起始 revision；每个高风险动作有独立动作键，审批绑定动作参数、目标版本和到期时间。默认至少一次交付下仍应做到重复请求不重复创建发布、扣费或数据迁移。不能承诺框架让所有外部副作用 exactly-once。

断线重连优先使用 Eve 官方客户端与事件游标，再映射为平台事件。模型说“成功”不是事实来源；命令退出码、测试报告、浏览器断言、产物校验和发布健康检查才是状态推进依据。

## 四、阶段总览与发布边界

主路径为 P0 技术基线 → P1 平台与隔离地基 → P2 应用构建闭环 → P3 可恢复工作台 → P4 受控发布 → P5 全栈应用 → P6 生产准入。P7 是已有仓库和可视化编辑等扩展，不是 P6 的前置条件，可以在 P4 后按用户反馈排优先级。

P2 完成后只适合开发者内测；P3 完成后形成可恢复的内测工作台；P4 完成且通过安全门槛后，可邀请小范围白名单用户使用前端应用 MVP。P5 扩展到全栈邀请测试；P6 通过后才评估商业开放。安全、评测和可观测性从 P0 开始，P6 是集中加固与发布审查，不是首次实现它们。

暂不按日历承诺整体工期。先完成 P0，了解模型效果、环境限制、每日投入和预算，再用实际迭代速度估算后续工作。学习型开发按可验收纵切推进，而不是一次性生成整个平台。

## 五、逐阶段实现目标

### P0：技术基线与风险验证

**目标。** 先证明现有模型、Eve 运行方式和候选沙箱能支撑应用构建，不先写完整工作台。沿用当前主 Agent 配置，评估 `eve/extensions/code` 是否能满足基本编码需求；不把“安装了 Eve”当作已挂载编码扩展。

P0.1 是环境基线：确认本地 Node 26、锁文件、Eve 版本及所需凭据的配置位置，运行 typecheck、build 和一轮最小对话。只记录凭据是否就绪，不把值写入日志、文档或 Git。若环境不支持，不顺手升级依赖或换模型，先报告阻塞原因。

P0.2 是沙箱探针：用同一个候选 provider 完成创建工作区、写入测试文件、执行受限命令、停止、恢复、删除；验证文件是否仍在、进程是否结束、端口是否能暴露和关闭。记录隔离、出口控制和费用限制的真实支持情况。没有预览授权能力时，先限制操作者内测，不发布公开链接。

P0.3 是最小生成实验：基于固定的 React/Vite/TypeScript 模板，让 Agent 完成一个页面和一次增量修改，执行真实 build 并启动预览。注入一个可控编译错误，观察其能否基于错误修复；证明模型调用了工具并生成真实文件，而非仅返回代码文本。记录成功和失败，不掩盖失败样本。

P0.4 是恢复实验：分别测试浏览器断线重连、同版本 runtime 重启和沙箱空闲恢复。三者解决不同问题；必须逐一记录 Eve 负责的部分与平台仍需实现的部分。确认可恢复不意味着所有外部动作可安全重试。

P0.5 是收敛决策：形成 `docs/adr/` 下的技术决策与一份基线报告，记录有效配置、模型实测、provider 限制、部署候选、源码持久方案和已知风险。未来代码路径属于建议，不在本轮预先创建空模块。

**通过门槛。** 一轮真实工具调用、一个可构建页面、一次增量修改和一次错误修复均有工具/命令证据；恢复实验有结论；预览访问、授权和资源清理有可行方案或明确阻塞。结果不满足时停在 P0，不能用截图或聊天回复代替验证。公开试用仍未开放。

**学习重点。** 理解 LLM、Agent runtime、工具、沙箱和应用服务器的边界；学会用最小实验排除最贵的架构风险。P0 成功后再决定 P1 的具体组件。

### P1：项目、身份、持久化和隔离地基

**目标。** 用户可以创建项目和工作区，平台知道“谁能操作什么”，并能从持久源码恢复，而不是只能依赖一个临时 session。

P1.1 建立最小 Web 壳与真实登录，使用成熟身份服务或库；持久化 User、Project、Membership、Run 和 Revision。平台鉴权边界覆盖 Eve session 的创建、续聊、流读取与控制请求，不向浏览器暴露可绕过授权的 runtime 入口。配置与日志输出按敏感字段脱敏。

P1.2 从受控模板初始化项目，保存初始 revision 和源码校验值。实现项目级租约、revision 乐观校验及请求幂等；同一个项目的第二次写入应明确排队或拒绝，而非悄悄覆盖。模板依赖和安装命令可复现，首次仅支持一个模板版本。

P1.3 封装工作区创建、文件访问、命令执行、保存快照、回收与恢复契约。实现文件 realpath/符号链接边界校验，限制读取和写入范围、输出长度、命令时长、进程数、磁盘与资源用量。依赖安装脚本也属于不可信代码，只在隔离执行面运行；网络策略限制云元数据、内网与非授权外部地址，具体能力由 provider 实测确认。

这里必须盘点实际暴露的全部默认与扩展工具，而非只保护新增工具。首版关闭共享沙箱的子 Agent 委派或证明其不会产生并行写入；限制后台进程并登记归属，以便取消、失去租约和回收时终止。应用 runtime 内的网络工具也需收口，不能只在沙箱施加出口限制而留下另一条不受控的 `web_fetch` 通道。依据 Eve 公开配置能力选择禁用、权限替换或受控包装，并以实际生效工具清单验收，不依赖 instructions 禁止。

P1.4 实现逐项目独立 origin 的私有预览通路：校验项目访问权、使用短期访问票据、不携带平台高权限 cookie，明确 iframe 与 websocket/HMR 的兼容边界。默认不让预览暴露到无鉴权公网；文件下载、快照与产物链接同样授权，日志不泄露签名 URL。负例不仅是用户 B 访问 A 的 ID，还包括用户打开一个不可信项目后，该预览不能同源读取其另一个项目或注册影响其他项目的 Service Worker。

P1.5 在服务端实施最小硬限额：每用户并发数、每项目写入数、Run 最大时长、工具次数与模型用量、沙箱资源/TTL。启动前原子预留容量和用量额度，不足则拒绝；结束或租约失效后释放，未能确认的在途费用保守保留并对账。P2 必须将这些限制连到真实工具与模型执行，P6 只加固账本、计费和运营，不首次实现预算控制。

**交付与通过门槛。** 用户 A 创建的项目、session、流、文件、快照、预览和控制接口，用户 B 即使知道 ID 也无法访问；重复提交不产生重复 Run；同时写入被串行化；删掉沙箱后能从持久 revision 恢复源码并核对校验值；取消、超时和回收不遗留计费资源。测试“旧执行者失联 → 租约到期 → 新执行者开始 → 旧执行者恢复”，证明旧执行者不能污染当前工作区、提交版本、推进状态或发布。并发预算申请不能超额放行，超限后默认工具与业务工具均不能绕过限制。先用自动化双用户和故障测试，再进行手工验证。

**学习重点。** 身份认证不等于资源授权，沙箱不是数据库，租约需要过期与续约，取消也需要释放资源。实现可放在拟议的 `apps/web/` 与 `platform/`，但应先以少量模块完成纵切，不为未来拆服务提前制造复杂度。

### P2：真正可验证的应用构建 Agent

**目标。** 输入需求后，Agent 可以定位文件、实施最小修改、运行检查、依据失败有限修复，并产出可追溯结果；目标不是“更长的提示词”。

P2.1 修改既有 `agent/instructions.md`，定义固定模板约束、需求澄清、增量修改、检查与完成判据。使用现有文件工具和已核实的编码扩展，不重复造一套通用 read/write/bash。仅为项目能力增加边界明确的工具，例如读取项目上下文、执行固定验证流程、创建预览和保存 revision；工具名称与定义形状在阅读对应 Eve 文档后确定。

P2.2 通过可信上下文绑定 project、workspace、run 和授权主体，不接受模型自行声明的 tenant 或工作区路径作为权限依据。需求与仓库文本都视为不可信数据；文档里的指令不能提高工具权限，平台凭据不能进入模型上下文。发布、删除外部资源和生产数据操作不纳入默认可自动执行范围。

P2.3 实现轻量任务摘要与工具证据展示，限制读取量、上下文长度、最大轮次、修复次数、单命令时间和 Run 总预算。初始修复最多 2 次是可调产品策略，不是无限循环；取消后停止新工具调用并终止关联进程。大输出截断并保存受控 artifact，不把完整依赖目录塞入上下文。

P2.4 尽早建立 evals：固定模板、任务输入、模板版本、模型、检查命令和环境。首批用 12 个任务覆盖新建页面、路由、样式修改、交互、局部变更保护和故意构建失败，另设确定性权限与状态机测试。模型质量用多次真实运行衡量；协议和状态边界用独立 fixture agent，不改主 Agent 模型。

**交付与通过门槛。** 每个成功 Run 都保存起始/结果 revision、diff、检查命令、退出码、产物和用量。首次闭环对约定的 3 个任务各跑 3 次，至少 8/9 次达到预设功能检查；失败都明确终态，没有假成功、越权或无限运行。12 个任务集跑完并报告基线，暂不将小样本成功率包装成生产承诺。编译通过与交互正确分开统计。

**学习重点。** 完成判据、工具权限、错误分类、上下文预算、有限反馈循环和 eval-driven development。先把一个 Agent 做可靠，再讨论多 Agent。

### P3：可恢复工作台、预览与 Save Points

**目标。** 把开发者能跑的闭环变成用户能理解、修改、恢复的产品体验。工作台先完成对话、只读文件树、日志/检查证据和预览，再增加编辑器与 diff，避免先做复杂 IDE。

P3.1 通过 Eve 官方客户端接入消息、工具事件、取消和重连。页面刷新后按稳定 project/run/session 标识恢复；把失败、等待审批、预览启动中、预览失效分别展示，而不是统一显示“生成中”。事件去重和状态归并避免重复卡片与旧状态覆盖新状态。

P3.2 文件树、编辑器和 diff 对应真实 workspace/revision。Agent 执行期间手动编辑只读；保存编辑时带 revision 前置条件，冲突明确提示。所有写入仍经 P1 租约与授权，不能只靠 UI 禁用。

P3.3 每轮开始前保存基线，结束后保存成功版本或标记为失败/取消的草稿。Save Point 关联源代码、工具链和模板版本、检查证据及必要配置引用，但不保存明文密钥。采用不可变快照加数据库版本关系，Git 历史可后续接入，不因尚无 GitHub 而延迟恢复能力。

P3.4 回退创建新的当前 revision 并重建预览，不覆盖历史；失败草稿可查看 diff、放弃或继续修复。空闲沙箱恢复时受控重启预览进程并做健康检查。源码导出过滤平台凭据、缓存和环境文件，下载受访问控制。

**交付与通过门槛。** 完整演示创建应用、追加需求、打开真实文件、查看 diff、回退版本、导出源码；刷新/断网后仍定位同一任务，不重复执行修改；沙箱停机恢复后预览可用；两个标签页同时编辑不能静默覆盖。回退前后源码与预览内容一致，失败 Run 不覆盖最后成功版本。

**学习重点。** 流式协议与 UI 状态、乐观并发、不可变版本、执行状态与展示状态、源码真源与缓存的区别。到此可形成内测 Alpha，但尚不是面向用户的生产托管平台。

### P4：受控发布，形成前端 MVP

**目标。** 将某个明确版本发布为可访问应用，而不是把沙箱开发服务器当线上站点。首版只支持一种适配静态前端的发布目标，不同时接多家云。

P4.1 定义发布适配器、Deployment 记录和不可变构建产物。发布固定 revision，在受限构建环境使用锁文件重建；部署凭据通过服务端受控通道使用，Agent 与生成应用都不能读取平台发布密钥。

P4.2 发布由用户显式批准，展示目标环境、revision、已通过检查和预期费用；审批绑定构建产物或版本，之后修改代码应使旧审批失效。重复点击、网络重试、Webhook 重复和乱序都不应创建重复有效发布或覆盖较新状态。

P4.3 发布后做健康检查，只有通过才推进当前线上指针。支持重新发布、解除发布和回退到前一个可用产物；失败保留旧站点并显示失败证据。默认使用供应商域名，自定义域名与证书自动化后置。

**交付与通过门槛。** 从需求到预览再到确认发布是一条连贯操作；部署指向准确 revision；模拟构建失败、供应商错误及重复回调时不污染线上；回退后健康检查通过。明确部署 Agent 平台与部署用户生成应用是不同流水线，平台的 Vercel 操作仍按项目要求走 Eve。

**学习重点。** Artifact promotion、审批 TOCTOU 风险、幂等外部副作用、环境隔离和发布状态机。通过 P1–P4 安全与质量门槛后，前端 MVP 才适合白名单邀请使用。

### P5：全栈应用、认证与数据库生命周期

**目标。** 从“可发布前端”升级为“用户真正能使用的带账户应用”。只新增一个受支持全栈模板与托管组合，不向模型开放任意数据库或任意生产服务器。

P5.1 选择适配发布目标的后端模板、成熟登录组件和数据库方案，先实现任务管理应用的标准纵切：注册/登录、每用户数据隔离、CRUD、输入校验和错误处理。示例认证和数据权限写成经过测试的模板，不让每个项目从零生成安全敏感基础设施。

P5.2 平台保存开发、staging、生产环境的资源映射与密钥引用，分开数据库和最小权限身份。Agent 默认仅可操作开发环境；生产迁移通过固定通道、人工审批和审计，不能因为用户一句含糊需求就直接修改线上数据。

P5.3 建立版本化迁移、迁移预检、备份、恢复演练及 schema 兼容策略。代码回退不能宣称同时回退数据库；优先使用向后兼容迁移，破坏性变更需要停机/数据恢复计划和明确确认。测试数据不默认复制到线上。

**交付与通过门槛。** 浏览器端到端测试证明两个应用用户互相看不到数据；开发数据不出现在生产；旧版本代码与新 schema 的兼容或拒绝路径明确；通过一次备份恢复演练并核对数据。全栈发布健康检查涵盖登录和关键数据操作，不能只有首页 HTTP 200。

**学习重点。** 平台用户与应用用户分离、后端授权、数据库迁移、Secrets 管理、schema/代码版本耦合。完成后进入全栈 Beta，不代表可承载敏感数据或任意合规场景。

### P6：可靠性、安全与商业发布准入

**目标。** 将前期已有的基础保护变成可量化、可运维、可审计的保障。此阶段不新增主要产品类型，集中处理故障、资源滥用、升级、数据恢复与成本失控。

P6.1 建立从 request/project/run 到 Eve session、工具、沙箱、构建和 deployment 的关联观测。统计任务成功率、失败分类、首个可用预览耗时、取消时延、模型与沙箱成本、资源泄漏及发布健康率。业务事件不依赖聊天文本解析，日志默认脱敏并定义保留期。

P6.2 对 runtime 重启、供应商超时、模型限流、工作区丢失、事件重复、进程失联和部署中断实施故障注入。恢复优先复用 Eve；外部动作做幂等与对账。不可安全重试时进入 interrupted 并让用户选择恢复方式，不能默默重复迁移或发布。

P6.3 做执行沙箱、预览 origin、对象存储、下载链接、session/stream/control、供应链安装脚本和生产密钥的威胁建模与复核。测试至少两个独立用户之间的访问边界；跨租户若尚未实现就不宣传多租户。浏览器 preview 的隔离与服务端沙箱隔离必须分别验证。

P6.4 完成配额和用量账本、原子预算预留、硬性停止和账单对账。Run 额度覆盖模型、沙箱、构建、存储和发布，而不仅是 token；支付先用测试模式或人工额度验证。超预算停止新动作，已发生费用有可核对记录，不承诺不存在在途用量。

P6.5 建立 CI 门禁、灰度、告警、应急手册、数据删除/保留策略和升级演练。固定或受控升级 Eve 与模板依赖，验证旧 session 恢复和事件适配兼容；生产配置不依赖本地开发 world。高风险开放前安排独立安全审查，必要时采用外部审计。

平台自身的回退要覆盖 runtime 版本、平台元数据 schema 和持久 session，而非只回退前端代码。P0 选定 world 后记录支持矩阵：哪些 session 能原地续跑，哪些要保留旧部署，哪些只能中断后基于 revision 新建。P6 实测升级后回退：新旧平台版本均能处理兼容的元数据，已进入新 checkpoint 的 session 不被错误交给旧 runtime；不兼容时明确排空或中断策略。生成应用回退、平台升级回退和灾难恢复是三类不同操作。

**交付与通过门槛。** 用下文质量指标验证邀请测试数据和故障演练；严重安全缺陷全部关闭；备份、恢复、升级、配额和回滚有证据。商业开放是单独的 go/no-go 决策，不因“阶段代码写完”自动发生。

**学习重点。** SLO、威胁模型、故障恢复、容量与成本管理、可审计账本和安全发布。工业级意味着在失败时仍可解释、限制损失并恢复，而不是永不失败。

### P7：按需求扩展，而不是首版全做

已有仓库工作流优先考虑 GitHub App 的仓库选择与短期凭据，在独立分支上分析、修改、执行检查并创建 PR。默认不直接推主分支；限制仓库体积、支持语言和依赖安装风险。通过门槛是两个受支持仓库的任务可验证、授权可撤销、失败不覆盖用户未提交变更。接入前先查 Eve registry 和 `eve/extensions/git`，不要假设 code 扩展自带 GitHub 能力。

可视化编辑先做“选择元素 → 收集 DOM/截图/源码定位证据 → 提出变更 → 预览确认”，不直接字符串替换任意 HTML。将元素映射回 React 源码是独立难点；动态渲染、组件复用、响应式布局和无法定位时必须有降级路径。先证明受支持组件的稳定定位和回退，再宣传通用可视化编辑。

模板库、多模型选择、团队角色、自定义域名可按真实使用频率逐个进入。多模型先经过同一任务集比较成功率、延迟、成本与能力支持；不预设“更强模型”必然适合所有任务。实时协作和多 Agent 并发只有在单写者架构确实成为瓶颈、且有冲突处理方案时才立项。

Android、Shopify、自带 SSH 与自建托管属于各自独立的产品与安全工程，不是现有闭环里再加一个工具就完成。每个扩展都应有自己的用户旅程、风险评估和验收任务集。

## 六、质量指标与生产准入建议

以下数字是待 P0 基线校准的初始目标，不是已测结果或对用户的 SLA。每次报告同时给出样本量、模板/模型/环境版本、失败原因和成本，不能只公布一个成功率。

**任务正确性。** P2 的 12 个固定任务每个至少运行 3 次，保留全部尝试。P4 前要求至少 90% 的任务运行通过各自构建、行为和需求断言；P6 扩展到不少于 30 个代表任务，每个至少 3 次，初始目标仍为至少 90%，且核心发布流程没有已知阻塞。这个小样本只作发布门禁，不能外推为通用编码准确率；真实用户任务另做分层统计。

**安全与真实性。** 自动化负例覆盖跨用户资源访问、非法路径、预览票据失效、审批参数改变、越权控制和敏感信息泄露；发布前必须全部通过，严重缺陷不得豁免。所有标记成功的运行必须有检查证据；出现假成功时阻断发布并补回归用例。测试通过不等于证明没有未知漏洞。

**时延。** 固定单页模板和基准环境后，初始将冷启动首个可交互预览的 p95 控制在 180 秒以内，后续局部修改 p95 在 60 秒以内；达不到时先分解模型、依赖安装、构建和预览耗时，再决定缓存或调整目标。样本少时报告每次耗时，不滥用分位数。

**恢复与取消。** 注入断网、重启、沙箱丢失、重复请求等故障，各场景至少运行 10 次；不得丢失已经确认持久化的 revision，不得重复高风险外部动作。初始目标为取消后 10 秒内停止新工具动作、30 秒内停止相关沙箱进程；如供应商做不到，明确降级与成本边界。

**数据恢复。** 已确认的源码 revision 在单沙箱丢失测试中目标 RPO 为 0；这不等于数据库区域级灾难 RPO 为 0。P6 前建议在独立备份上完成一次平台元数据与源码恢复演练，初始灾难恢复目标为 RPO 不超过 24 小时、RTO 不超过 4 小时，再根据所选存储能力和用户需求修订。

**成本。** 先记录每次任务的模型用量、沙箱分钟数、构建与发布费用及成功任务平均成本，再由实际供应商价格和用户预算设定金额上限。不在未知价格时拍定“每次任务多少钱”。预算预留和硬限制必须有自动化测试；不以客户端计数作为扣费真源。

**运营。** P6 要能识别并告警异常失败率、停滞任务和资源泄漏，确认备份可恢复、供应商故障可暂停新任务、旧部署可继续服务。可用性目标在小范围 Beta 形成足够数据后再承诺，不用一次压测宣称达到高可用。

## 七、安全与可靠性贯穿路线

P0 阶段只使用操作者测试数据和非生产凭据，核实能力边界；P1 开始执行资源授权、隔离、源码持久化、私有预览和配额；P2 引入行为评测、有限修复和工具证据；P3 提供版本恢复和写入冲突控制；P4 引入发布审批与产物回退；P5 才允许受控的生产数据生命周期；P6 将这些控制统一做故障演练与独立复核。

不要以提示词代替权限，不以命令黑名单代替执行隔离，不以请求鉴权代替资源授权，不以“文件在沙箱里”代替持久化，不以“build 通过”代替应用功能正确，也不以“有日志”代替可审计用量和恢复能力。

特别需要区分平台管理密钥、生成应用的环境密钥和用户授权的第三方凭据。它们有不同生命周期与权限，不能统一注入 Agent shell。删除项目需要覆盖关联沙箱、快照、构建产物和凭据引用，并按既定保留策略处理备份；“在项目列表隐藏”不等于删除完成。

## 八、我们如何边实现边学习

每个小迭代采用相同节奏：先用一个具体用户故事解释目的，再画出最小请求路径或状态变化；只实现一个可演示的纵切；先写确定性测试与必要失败用例，再接入真实模型评测；最后演示成功与失败路径、检查 diff，并把设计取舍记入 ADR。不要一轮交付十个服务后再补解释。

建议每次协作只处理一个有独立验收的小目标。实现前说明会修改哪些文件及原因，实现后解释调用链、关键类型、信任边界和最值得阅读的一处代码；由用户亲手运行测试、修改一个规则或复现一个失败。下一次迭代基于结果继续，而不是反复重写整份架构。

每阶段应留下可运行实现、最小测试或 eval、演示证据与短复盘。文档放 `docs/`，决策放 `docs/adr/`，Agent 行为测试沿用现有 `evals/` 入口，平台单元/集成测试和浏览器 E2E 随对应代码建立。是否拆为 monorepo、packages 或独立服务应在出现实际依赖边界时决定，不提前创建大量空目录。

### 第一次实现只做什么

建议下一步只执行 P0.1 的环境与基线检查：在用户本机或与 Node 26 及依赖平台匹配的环境确认版本，使用锁文件所需的安装方式，运行 `npm run typecheck`、`npm run build`，确认必要凭据后跑一轮最小对话。环境检查本身不应触发云部署、支付、凭据轮换或依赖升级；真实模型调用可能收费，执行前说明。

第一次交付应是一份短基线结果：哪些检查通过、哪些被环境阻塞、现有模型能否完成基本工具调用，以及下一项 P0.2 验证需要什么条件。若检查发现问题，先解释并修复最小问题，不同时搭工作台、数据库和 GitHub 集成。

下一轮可以直接提出：“从 P0.1 开始，先解释检查目标与命令，再执行，不更换模型，也不部署。”这会让学习过程从可理解的基线出发。

## 九、暂未验证与后续决策

本轮是静态项目检查与公开产品资料核实，没有运行 typecheck、build、eval、真实模型、沙箱或部署。因此不应将本文的框架文档能力当作本项目实测能力，也不应根据开发日志推断当前系统运行正常。

待 P0 核实的事项包括模型可用性与编码表现、真实生产 Workflow world、沙箱供应商及端口/网络/停止恢复能力、部署目标限制和成本。待 P1 记录的决定包括 Web 框架、身份服务、元数据与源码存储，以及项目与 Eve session 的生命周期关系。待 P4/P5 确定的事项包括生成应用的托管、全栈模板、数据库与区域要求。

现阶段不建议为了“工业级”立即引入 Kubernetes、微服务、向量数据库、复杂 RAG、多人协作算法、多 Agent 调度或全语言索引。只有任务集和真实使用数据表明简单方案已成为瓶颈，且收益覆盖维护成本时，再增加相应复杂度。

路线是否有效，最终看用户能否稳定完成“创建 → 修改 → 验证 → 恢复 → 发布”，以及平台能否在错误、越权、超预算和环境故障时守住边界，而不是项目包含多少热门组件。
